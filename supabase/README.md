# Phase 2.1 database design (not applied)

Migration: `migrations/20261031000100_phase_2_1_schema.sql`.
The website, mock trips, and matching algorithm remain unchanged. No Supabase client or credentials are configured. This is a one-time migration for a fresh schema, not an idempotent script for tables that already exist. Review before applying with a trusted migration role.

## Data and application mapping

- `profiles.id` references `auth.users.id`; nickname and short bio are self-managed and readable only by that user. Profiles are created explicitly after signup; no Auth signup trigger can break registration. Trips and participants reference Auth IDs directly, so profile creation is not required for referential integrity.
- `trips`: `from` → `origin`, `to` → `destination`, `date/time` → `departure_date/departure_time`, `flexibility` → `time_flexibility_minutes`, `traveling` → `existing_traveler_count`, `seats` → `additional_companions_requested`. Luggage codes and limits mirror the existing form. Existing count includes the organizer. Departure date/time are California civil time, with timezone-explicit future checks.
- `trip_participants`: one unique `(trip_id, user_id)` request, immutable `party_size` (includes the applicant), and pending/approved/rejected/withdrawn status. Owners cannot join their own trips. Deleted Auth accounts cascade to their owned trips, profiles, and requests; deleted trips cascade to their requests. This is a deletion policy, not an audit archive.
- Do not store a writable `availableSeats` counter yet. Future matching should derive availability from recruitment limit minus approved party sizes, without changing the matching algorithm. `existing_traveler_count + additional_companions_requested` is not a vehicle seating guarantee.

## Access rules

- RLS is enabled on all three tables. Anonymous roles receive no privileges; authenticated roles receive explicit minimum table/column privileges. No client deletion is granted.
- Only authenticated users whose **current Auth email** is confirmed and exactly in the `ucdavis.edu` domain can create trips or submit join requests. A private, fixed-search-path SECURITY DEFINER helper reads only the caller's Auth record and returns a boolean. It rejects currently banned and anonymous Auth users and does not trust JWT email, profile claims, or user-editable metadata. No email data is returned. This relies on Supabase Auth's email confirmation flow and trusted administrator/provider configuration; it does not prove current enrollment.
- Keep `davis_private` outside exposed Data API schemas. Only the verification helper is executable by authenticated callers; trigger functions are not callable directly. Explicit private schema/function revocations also remove possible service-role default grants. The participant trigger is SECURITY DEFINER solely to lock/read its parent trip without granting applicants UPDATE rights over other owners’ trips; it independently checks caller identity, eligibility, state and allowed transitions. Other trigger functions explicitly remain SECURITY INVOKER. All functions use an empty search path. The migration must be owned by a trusted database/migration role. Service-role credentials and database owners can bypass RLS; never expose them to clients.
- Profiles are self-only, including reads. There is no public email/contact directory. Future display of another user’s nickname requires a deliberately scoped endpoint; do not weaken profile RLS just to support a public join. A future trip-scoped nickname endpoint must first authorize access to that trip, then return only the intended nickname, never the profile bio, email or other Auth fields. Do not add a default owner-rights view over profiles: it can bypass profile RLS. A security-invoker view preserves RLS, but consequently cannot display other users’ nicknames with the current self-only policy. Public-to-the-internet nickname display needs a separate explicit privacy decision; it is not enabled here.
- Verified users can browse active future trips. Owners can read their own trip history and edit their own active future trips while verified. Closing is a status-only operation: cancellation/completion cannot also rewrite the trip. Completion requires the original departure to have passed. Cancelled/completed trips cannot be edited or reopened, and departed trips cannot be rescheduled back into active listings. Owners who lose university verification may still cancel their own active trips (status only), but may not edit other fields or complete them. Origin, destination and notes are visible to verified browsers: use public meeting places, not home addresses or contact details. Free-text constraints cannot prevent users from entering private information.
- Only the applicant or trip owner can read a participation record. Other travelers cannot enumerate the roster. Trip ownership and request identity/party size cannot be changed. Timestamps are server-managed. There are no cyclic policy dependencies.
- Applicants may withdraw pending requests; owners may reject pending requests, including after the trip is cancelled/completed. Existing requests are retained as private history; closure does not automatically reject or delete them. The owner can still see requests for a closed trip, and the applicant can still see their own request, but this does not grant the applicant access to the closed trip itself. Other status transitions, including self-approval **and owner approval**, fail in the trigger. Rejected/withdrawn requests cannot be reset, replaced, or resubmitted by clients in this phase. The unique constraint prevents concurrent duplicate requests.

## Required before enabling approvals / real bookings

Approval is deliberately disabled, not implemented with a non-atomic RLS count check. Pending requests do not reserve seats. The insert policy and locked trigger check that the requested party could fit the trip’s current recruitment limit; multiple pending requests may exceed that limit.

Implement an audited transactional PostgreSQL RPC (called by a trusted server or properly scoped authenticated API) that:

1. Authenticates the caller, verifies current eligibility, checks trip ownership, and forbids approving the caller's own request.
2. Locks the parent trip row with `SELECT ... FOR UPDATE`, then locks the request in a consistent order. Rechecks trip status, departure, applicant eligibility and request state inside the transaction.
3. Sums approved `party_size` and ensures the new approval stays within `additional_companions_requested`. Updates approval atomically; repeated requests must be idempotent.
4. Uses the same parent-row lock for capacity reductions, party-size changes, cancellations, withdrawals of approved requests, and any other capacity-affecting operation. Prevents owners reducing capacity below accepted occupancy. The current generic trip edit path must be restricted or extended before approvals are enabled.
5. Replaces/extends this migration's fail-closed status trigger in a reviewed migration; a SECURITY DEFINER function alone does not bypass the trigger. Restricts EXECUTE grants and sets a fixed search path. Never use a browser-supplied owner ID as authorization.

Also define route/time edits after approval, cancellation notifications, account deletion effects, rate limits, abuse controls and DST ambiguous/nonexistent departure-time handling. For now, no approval path exists, so this schema does not claim to implement seat reservations or concurrent booking protection. New join inserts now acquire a parent `FOR SHARE` row lock and recheck the current status, departure and limit. This conflicts with owner trip updates, fixing join-versus-cancellation/completion/edit races. If closure commits first, a waiting join fails. If a join commits first, later closure can succeed and the request becomes history. At stronger isolation, callers must retry serialization failures; multi-trip transactions can also deadlock and need full transaction retry. This is not seat-reservation protection: pending requests do not consume capacity.

## Review changes and validation

The pre-application review fixes the concurrent join/closure race with a restricted trigger, makes closure status-only, allows cancellation after loss of university verification, rejects currently banned users for verified actions, and tightens text/date constraints. Dates must be finite years 0001–9999, text limits apply to the full stored value, whitespace-only labels are rejected, and distinct-endpoint checks normalize case and repeated whitespace. Business-time trigger checks use real clock time after lock waits. The fresh-schema migration deliberately fails if `davis_private` already exists rather than trusting unknown pre-existing ownership.

All three tables retain RLS and minimum column grants. No DELETE/TRUNCATE, identity changes, client timestamp writes, direct approval or public profile access is enabled. Future approval still requires the separate capacity transaction described above. Do not add FORCE RLS blindly: trusted migration/function ownership and deliberate RLS bypass for the narrowly scoped Auth/locking helpers are part of this design.
